所以 `mvn spring-boot:run` 开箱即用。换机器或换密码时，改这个文件即可，
或在启动前设 `DB_PASSWORD` 环境变量（优先级更高）。

## 5. 已修复：Maven 本地仓库的 85 个损坏 POM

### 症状

任何 Spring Boot 3.5.16 项目构建时立刻失败，报：

```
Non-parseable POM ...spring-boot-dependencies-3.5.16.pom:
only whitespace content allowed before start tag and not \u0
(position: START_DOCUMENT seen \u0... @1:2)
```

### 根因

`F:\JavaTool\Maven\maven_repository` 里有 **85 个 `.pom` 文件整份都是 NUL 字节**
（零填充）。文件时间戳统一为 **2026-10-12 14:32**，属于一次被中断的下载
（典型成因：下载中途磁盘写满或进程被杀，文件被预分配但内容从未写入）。

这些文件恰好覆盖 Spring Boot 3.5.16 的**完整 POM 依赖闭包**：spring-boot-dependencies、
各 starter、Spring Framework 6.2.19、Jackson 2.21.4、Micrometer、Tomcat 10.1.55、
以及一大批 BOM（netty / reactor / junit / mockito / testcontainers / jetty …）。

Maven 不会校验本地已存在文件的校验和，所以这些文件会一直被当成有效缓存复用 ——
**不清理就永远构建不了**。

### 处理

```powershell
# 1) 扫描（Node 脚本；用 PowerShell 逐个读 2 万个文件会慢到不可用）
node docs\scan-corrupt-maven.js "F:\JavaTool\Maven\maven_repository" docs\corrupt-maven-files.json

# 2) 删除命中的文件（默认只删 .pom 及其同名 .sha1 / .lastUpdated；同目录 .jar 不动）
node docs\repair-corrupt-maven.js --repo "F:\JavaTool\Maven\maven_repository" --list docs\corrupt-maven-files.json

# 3) 重新构建，-U 强制校验并重新下载
cd backend
mvn -U -DskipTests package
```

实际结果：删除 170 个文件（85 个 `.pom` + 85 个同名 `.sha1`），共约 1.1 MB；
`mvn -U` 重新下载后 **BUILD SUCCESS**。

`docs/corrupt-maven-files.json` 是当时的命中清单，保留下来作为记录。
同目录下的 `.jar` 全部完好，未被波及 —— 因此这次损坏只影响 POM 解析阶段。

### 如何再次判断

出现下面任一情况，先怀疑同类问题：

- `Non-parseable POM ... not \u0`
- 构建在 `Scanning for projects...` 之后立刻失败，且指向本地仓库里的某个 `.pom`
- `mvn` 报 `Could not open file channel for ... .locks/artifact~...`

第三条是**权限/沙箱**问题（Maven 无法写本地仓库），不是文件损坏，两者要区分。

## 6. 已写入 AGENTS.md 的踩坑点

搭建过程中实际踩到、且以后会再遇到的：

1. **PowerShell 5.1 的 `Get-Content` 默认按系统 ANSI 代码页（本机 GBK）读取无 BOM 的
   UTF-8 文件。** 把含中文注释的 `.ps1` 读成乱码后，会引发莫名其妙的
   `表达式或语句中包含意外的标记` 之类语法错误。**读文本一律显式加 `-Encoding UTF8`。**

2. **`.ps1` 可能因执行策略/文件封锁而无法直接运行**（本机
   `LocalMachine = RemoteSigned`）。实测直接 `& script.ps1` 被拒。三个办法：
   `Unblock-File`、`-ExecutionPolicy Bypass`、或改用 ScriptBlock 执行。
   本仓库的辅助脚本因此全部写成 **Node（`.js`）** —— 不受执行策略约束，也不受代码页影响。

3. **`pwsh` 不是命令。** 只装了 Windows PowerShell 5.1。写脚本别用 PS7 专有语法，
   也不要尝试嵌套 `pwsh -File`。

4. **`mvn test` 依赖真实基础设施。** `MyAppApplicationTests` 是 `@SpringBootTest`，
   启动时会连 MySQL 和 Redis。没建库或没配密码时必然失败 —— 那是环境问题，不是代码问题。
   只验证打包用 `mvn -DskipTests package`。

5. **前端 `pnpm build` 会先跑 `vue-tsc`**，类型错误会中断构建；而 `pnpm dev` 不会报同样的错。
   提交前跑 `pnpm type-check`。

6. **若在 DSH 的沙箱模式（workspace-write）下构建**，Maven 与 pnpm 都会失败：
   它们要写 `F:\JavaTool\Maven\maven_repository`、pnpm store 和 npm 缓存，
   全都在工作区之外，且联网下载也被限制。这类失败是**预期的沙箱行为**，
   表现为 `[sandbox: file access denied under workspace-write mode]` 或
   `EPERM ... .locks/...`。要么把该次命令放到完全权限下执行，要么由你在终端里自己跑。

## 8. 端口

| 服务 | 端口 | 说明 |
|---|---|---|
| 后端（Spring Boot） | 8080 | `server.port` |
| 前端（Vite 开发服务器） | **3000** | 见下方警告 |

### ⚠️ 为什么前端不用 5173

Vite 默认端口 5173（以及回退的 5174）落在 **Hyper-V 预留的 TCP 端口段
4990–5188** 内，绑定会直接失败：

```
Error: listen EACCES: permission denied 127.0.0.1:5173
```

Hyper-V / WSL / Docker 会向系统预留大段端口，这是 Windows 上的常见现象。
查看本机保留区间：

```powershell
netsh interface ipv4 show excludedportrange protocol=tcp
```

实测本机保留段：`4989-5088`、`5089-5188`、`8029`、`8997`、`9579-9678`、
`12114-12213`、`13197-13396`、`13397-13496`、`13597-13696`、`50000-50059`。

实测可用：3000、8081、9000、18080。前端因此固定在 **3000**，
并在 `vite.config.ts` 里显式 `host: '127.0.0.1'`
（默认 `localhost` 会先解析到 IPv6 `::1`，绑定可能另行被拒）。
